# Phase 12 仕様要決定リスト

ギミックエンジン・インベントリ・数字オブジェクトの実装（2026-06-10 時点）で表面化した、
実装を進める前に仕様を確定しておくべき項目の一覧。
各項目に現状の実装挙動と推奨案を記載する。決定後は `docs/world-creation.md` に反映し、
本ファイルの該当項目を消し込むこと。

関連実装: `Assets/Scripts/World/Gimmick/`（GimmickEngine / GimmickStateManager /
GimmickTimerLogic / GimmickValueResolver / GimmickInventoryLogic / NumberObjectSyncLogic）

## 1. ギミックルール定義のバリデーション層

**背景**: `RuntimeGimmickCondition` / `RuntimeGimmickAction` の StateIndex・TimerIndex が
範囲外の場合、`GimmickStateManager` / `GimmickTimerLogic` が `ArgumentOutOfRangeException`
を投げる。ワールド定義 JSON は UGC 由来のため、不正データで実行時クラッシュする経路になる。
数字オブジェクト（`NumberObjectSyncLogic.TryAdd`）は登録時拒否で対応済みだが、
ギミックルールは「JSON→Runtime 変換層（未実装）で検証する」前提のまま。

**決めること**:
- バリデーションの実施箇所: ① サーバー保存時（Go API）/ ② クライアント読み込み時 / ③ 両方
- 検証項目: StateIndex（ワールド 0〜9・プレイヤー 0〜3）・TimerIndex（0〜4）・
  イベント 1〜20 / 条件 0〜20 / アクション 1〜20・ルール+グループ合計 ≤ 100・
  ModEquals の modBy ≥ 2・文字メッセージ ≤ 80 文字・参照オブジェクト ID の実在
- 不正ルールの扱い: ワールド読み込み自体を拒否するか、該当ルールのみ無効化して継続するか

**推奨**: ③ 両方（サーバーは保存時に拒否、クライアントは防御的に該当ルールのみ無効化 + ログ）。
公開済みワールドの後方互換を考えるとクライアント側は「読み込み拒否」より「ルール単位の無効化」が安全。

## 2. 無限ループ判定のカウント単位（world-creation.md 9.10）

**背景**: 仕様は「1 回のイベント発火から連鎖するアクション実行数が 100 超」だが、
現実装（`GimmickEngine.MaxChainCount`）は「1 回の `Fire()` 内のアクション実行総数」でカウントする。
ルール上限 100 個 × アクション上限 20 個 = 正当なワールドでも 1 イベントで最大 2,000 アクションが
あり得るため、現行カウントでは誤検知する。一方、現エンジンにはアクションがイベントを誘発する
「連鎖」機構自体がまだないため、真の無限ループは現状発生しない。

**決めること**:
- 「連鎖」の定義: アクションが新たなイベント（ワープによるポータル利用・移動によるエリア侵入等）を
  同期的に誘発した場合のみカウントするのか、1 イベント内の全アクションをカウントするのか
- 上限値 100 の対象（連鎖深度 100 か、累計アクション数 100 か）
- 検知時の「ルームを初期状態にリセット」の正確なスコープ（項目 5 と関連）
- 公開前バリデーション（`WorldPublishValidator` のループ検出テストプレイ）との関係

**推奨**: カウント対象は「アクション実行が誘発した 2 次以降のイベント連鎖の累計アクション数」とし、
1 イベント直接のアクション実行（最大 2,000）は無条件で許可する。

## 3. 入室時同期スナップショットの不足分（world-creation.md 9.9）

**背景**: 9.9 のスナップショットは「ワールドステート / プレイヤーステート / タイマー /
進行中の移動」のみ。以下が含まれておらず、途中入室者が状態を再現できない。

**決めること（追加すべき同期対象）**:
- インベントリ保有状態（実装済みの `GimmickInventoryLogic.GetSnapshot()` 形式:
  playerId → objectId のマップ）
- オブジェクトの表示 / 非表示状態（ShowHideObject の結果）
- オブジェクトの種類切り替え状態（ChangeObjectType の結果）
- BGM オーバーライド状態（SwitchBgm の結果。14.5 の「状態リセットまで維持」を再現するため）

**推奨**: 上記 4 つすべてをスナップショットに追加し、9.9 の表を更新する。

## 4. インベントリの細部仕様（world-creation.md 9.3）

**背景**: 実装（`GimmickInventoryLogic`）は ID を不透明な文字列として扱っており、
以下が未定義のまま。

**決めること**:
- **ID の単位**: インベントリが保持するのは「配置オブジェクトのインスタンス ID」か
  「オブジェクト種別 ID」か。仕様の文言は「1 種別のオブジェクトを 1 個まで」で、
  「持つ」は特定の配置オブジェクトを消す操作のため、両者が混在している。
  「特定のオブジェクトを持っているか」条件が参照するのはどちらか
- **「持つ」アクションの対象「全員」**: 1 個のオブジェクトは 1 人にしか入らない。
  現実装はエフェクトを人数分発行し先着 1 名のみ成功する。「全員」を UI で選択不可にするか、
  先着 1 名仕様として明文化するか
- **取得失敗時の挙動**: 保有中オブジェクトの再取得・他プレイヤー保有中の取得は
  現実装では無言で失敗する。フラッシュメッセージ等のフィードバックを出すか

**推奨**: インスタンス ID で統一（条件もインスタンス指定）。「全員」は選択不可。失敗は無言で許容。

## 5. 「状態リセット」アクションのスコープ（world-creation.md 9.8 / 14.5）

**背景**: ResetState はステート（ワールド / プレイヤー）のみリセットする実装。
しかし 14.5 は「BGM オーバーライドは状態リセットまで維持」と定義しており、
どの ResetTarget が BGM を戻すのか不明。タイマー・インベントリ・オブジェクト表示状態を
含むかも未定義。9.10 のループ検知時「ルームを初期状態にリセット」のスコープも同様。

**決めること**:
- ResetTarget = World / All のとき: タイマー・BGM オーバーライド・オブジェクト表示 /
  種類切り替え状態・インベントリ・進行中の移動を初期状態に戻すか
- ResetTarget = InputPlayer / OpponentPlayer / AllPlayers のとき: 対象プレイヤーの
  インベントリを返却するか（現実装はステートのみ）
- 9.10 ループ検知時のリセットは ResetTarget.All と同一処理でよいか

**推奨**: All = 全要素（タイマー / BGM / オブジェクト状態 / インベントリ / 移動）を初期化。
World = ワールドステート + BGM + オブジェクト状態。プレイヤー系 = ステート + インベントリ返却。
ループ検知時 = All と同一。

## 6. 数字オブジェクトの細部仕様（world-creation.md 3.9）

**決めること**:
- **「ルーム参加 X 番目」の繰り上がり**: プレイヤー退室時に参加順番号が詰まる
  （現実装: 現在の在室者リスト順 = 詰まる）か、セッション中固定かつ欠番ありか
- **固定値の範囲と表示桁数**: ステート参照は 0〜255（3 桁）だが固定値の範囲が未定義。
  負数・桁数上限（描画メッシュ・テクスチャ設計に直結）
- **参照先プレイヤー不在時の表示**: 現実装は 0 を返す。「0 表示」か「非表示 / ハイフン」か
- **描画方式**: 桁ごとのメッシュ切り替えか、数字テクスチャアトラスの UV 切り替えか
  （Unlit 1 ドローコール制約との整合）

**推奨**: 参加順は「在室者の参加順で詰める」（現実装どおり）。固定値 0〜999（3 桁・負数なし）。
不在時は 0 表示。

## 7. テクスチャコスト判定の正確な定義（world-creation.md 4.3）

**決めること**:
- **「ギミックで非表示」の判定方法**: コスト対象外となる「非表示のオブジェクト種別」を
  エディタがどう判定するか。案: 「初期状態が非表示で、かつ表示に切り替えるアクションが
  ルール中に存在しない種別」のみ対象外（実行時に表示され得るものはコスト対象）
- **種類切り替え先に保存バリアントを指定できるか**: 現実装（`TextureCostCalculator` の
  `switchTargetTypeIds`）は ID を不透明に扱うためどちらでも動くが、UI とコスト計算で確定が必要
- **オブジェクトの初期表示状態**: 配置オブジェクトに「初期非表示」フラグを持たせるか
  （ワールド定義 JSON のフィールド追加）

**推奨**: 初期非表示フラグを JSON に追加し、「初期非表示 かつ 表示アクションなし」をコスト対象外とする。

## 8. ネットワーク権威モデルの明文化（world-creation.md 9.1 / 9.4）

**背景**: 9.4 は「ルール評価はルームオーナーが行い、結果を全クライアントに送信」とあるが、
9.2 のタイマーイベントは「各クライアントがローカル監視して発火 → オーナーが権威的に確認」とあり、
クライアント側でもエンジンを動かすのか曖昧。

**決めること**:
- エンジン実行はオーナーのみか（非オーナーは `GimmickEffect` リストの適用のみ行うか）
- タイマーイベントの検知責務: オーナーのみの監視で十分か（9.2 の記述の整理）
- 範囲乱数の共有方法: オーナー評価 + エフェクト送信モデルなら、エフェクトに解決済みの値
  （例: `WorldStateChangedEffect.NewValue`）が入るため追加の乱数同期は不要 — これを明文化するか
- エフェクト送信の形式（Netcode for GameObjects の RPC / NetworkVariable のどちらで運ぶか）

**推奨**: オーナーのみ評価・エフェクト適用方式（現エンジン設計と一致）。乱数の個別同期は不要と明記。

## 9. 人数変動イベントの入力プレイヤー（world-creation.md 9.5）

**決めること**:
- 退室時の「人数変動時」イベントで入力プレイヤーは誰か（退室者は既にいない）。
  退室者 ID のまま発火するか、入力プレイヤーなしか
- 発火タイミングと状態操作の順序: 退室者の `GimmickStateManager.RemovePlayer` /
  インベントリ返却の前か後か（条件「イベントに関わったプレイヤーのステート比較」の結果が変わる）

**推奨**: 退室者を入力プレイヤーとし、ステート削除・インベントリ返却の**前**に発火する
（退室者の最終状態を条件で参照できるようにする）。

## 10. 順位条件の詳細（world-creation.md 9.6）

**背景**: 条件「全プレイヤー中 X 番目に大きい / 小さい」（順位条件）は仕様表に記載があるが、
エンジン未実装（`GimmickConditionType` に種別なし）。

**決めること**:
- 同値の扱い（同率 1 位が 2 人いるとき「1 番目に大きい」は両方 true か）
- 対象プレイヤーが在室者全員か、入力 / 相手プレイヤーの順位を問うのか

**推奨**: 「対象プレイヤー（選択）の値が全在室者中 X 位以内」とし、同値は同順位（両方 true）。
